## Assignment: Fix Swift Concurrency Warning in MushafDatabase

**Context:**

During runtime testing of the jumpToError() optimization (commit e53498a), a Swift Concurrency warning was discovered in the console:

```
Potential Structural Swift Concurrency Issue: unsafeForcedSync called from Swift Concurrent context.
```

This warning is caused by the thread safety implementation added in commits a6f435c and b49bfc4, where we added `dbQueue.sync { }` blocks to serialize database access in MushafDatabase.

**Root Cause:**

The `MushafDatabase` class uses the old Grand Central Dispatch (GCD) pattern with `DispatchQueue.sync`:

```swift
public func getPageWords(_ pageNumber: Int) -> [(line: Int, words: [QuranWord])] {
    return dbQueue.sync {  // ← Called from Swift Concurrent context
        // SQLite database access...
    }
}
```

When these methods are called from SwiftUI views or other Swift Concurrency contexts (async/await), the runtime detects that we're using `DispatchQueue.sync` (old concurrency model) from within Swift's new concurrency model. This is considered unsafe and triggers the warning.

**Current Implementation:**

## Solution Approach

**Option 1: Convert to Actor (Recommended)**

Actors provide built-in serialization and are the Swift-native way to protect mutable state:

```swift
public actor MushafDatabase {
    private var layoutDB: OpaquePointer?
    private var wordsDB: OpaquePointer?

    // Remove dbQueue - actor provides serialization automatically

    public func getPageWords(_ pageNumber: Int) -> [(line: Int, words: [QuranWord])] {
        // No dbQueue.sync needed - actor serializes access automatically
        // ... existing implementation ...
    }

    // All other methods become async automatically
}
```

**Benefits:**
- Swift-native concurrency model
- Automatic serialization (no manual queue management)
- No warnings
- Type-safe

**Drawbacks:**
- All call sites must be updated to use `await`
- Changes propagate throughout codebase

**Option 2: Async/Await with Serial Queue**

Keep the queue but use async/await properly:

```swift
public class MushafDatabase {
    private var layoutDB: OpaquePointer?
    private var wordsDB: OpaquePointer?
    private let dbQueue = DispatchQueue(label: "com.memquran.database", qos: .userInitiated)

    public func getPageWords(_ pageNumber: Int) async -> [(line: Int, words: [QuranWord])] {
        return await withCheckedContinuation { continuation in
            dbQueue.async {
                // ... existing implementation ...
                continuation.resume(returning: result)
            }
        }
    }
}
```

**Benefits:**
- Maintains explicit queue control
- Async/await compatible
- No warnings

**Drawbacks:**
- More boilerplate
- Manual queue management still required

## Edge Cases to Consider

1. **Synchronous contexts calling async methods:**
   - ContentView methods that aren't async but need database access
   - Solution: Wrap in Task or make containing method async

2. **Multiple concurrent reads:**
   - Actor serializes all access (even reads)
   - May impact performance if many concurrent reads expected
   - Solution: Test performance; if issue, consider read-write lock pattern

3. **Database initialization:**
   - Actor initialization is synchronous
   - Database file opening should work as-is

4. **Shared singleton:**
   - `MushafDatabase.shared` works with actors
   - Actor ensures thread-safe singleton access
