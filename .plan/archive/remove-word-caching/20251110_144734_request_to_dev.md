## Assignment: Fix Performance Regression in Error Bookmark Navigation

**Context:**

The SQLite thread safety fix (commit b49bfc4) successfully eliminated all SQLite multi-threading errors ✅. However, manual runtime testing has revealed a **critical performance regression** affecting error bookmark navigation.

**Test Results Summary:**
- ✅ **SQLite errors eliminated** - Zero "illegal multi-threaded access to database connection" errors in runtime logs
- ✅ Regular bookmarks work instantly (as expected)
- ✅ Page jumps work instantly (as expected)
- ❌ **Error bookmarks take 10+ seconds** (was instant before fix)

**Root Cause Identified:**

`jumpToError()` in ContentView.swift:1311-1360 loops through **ALL 604 pages** sequentially:

```swift
for page in 1...604 {
    let pageWords = MushafCache.shared.getPageWords(page)
    // ... search for error word ...
}
```

With the new serial DispatchQueue in MushafDatabase, each `getPageWords()` call is serialized through `dbQueue.sync {}`. Looping through 604 pages × serial database access = 10+ second delay.

**Comparison with Regular Bookmarks:**

`jumpToBookmark()` (line 1469-1497) uses an efficient approach:
```swift
guard let page = MushafDatabase.shared.getPageForWord(
    surah: wordId.surah,
    ayah: wordId.ayah,
    position: wordId.position
) else { return }
```

This is **ONE database query** that returns the page number directly, then loads words from just that page.

## Task: Optimize jumpToError() Implementation

**Objective:** Make `jumpToError()` use the same efficient pattern as `jumpToBookmark()` instead of looping through all pages.

**Required Changes:**

### File: MemQuran/ContentView.swift

**Current inefficient approach (lines 1311-1360):**
1. Loop through all 604 pages
2. Load all words from each page
3. Search for error word
4. Search backwards for previous verse

**New efficient approach:**
1. Use `getPageForWord()` to find the page containing the error word (ONE query)
2. Load words from just that page (and possibly previous page if needed)
3. Search for previous verse

**Implementation guidance:**

The logic for finding the previous verse's last word is correct and must be preserved. The optimization is to:

1. **First, find the error word's page efficiently:**
   ```swift
   guard let errorPage = MushafDatabase.shared.getPageForWord(
       surah: wordId.surah,
       ayah: wordId.ayah,
       position: wordId.position
   ) else {
       writeLog("❌ Could not find page for error word: \(wordId.surah):\(wordId.ayah):\(wordId.position)")
       return
   }
   ```

2. **Load words from that page (and possibly nearby pages if needed for finding previous verse):**
   - Load the error page's words
   - The previous verse might be on the same page or the previous page
   - Consider loading 2-3 pages (error page and 1-2 pages before) to ensure we can find the previous verse
   - This is still massively faster than loading all 604 pages

3. **Preserve the existing logic for:**
   - Finding the error word in the loaded words
   - Searching backwards for the previous verse's last word
   - Handling edge cases (first verse of surah, etc.)
   - Computing the anchor word and jumping to it

**Edge Cases to Consider:**

1. **Previous verse on previous page:** The previous verse might end on the page before the error word's page. Loading 2-3 pages around the error should handle this.

2. **Beginning of Quran:** If error is in early verses where there's no previous verse on previous pages, handle gracefully (existing logic should already handle this).

3. **Cross-surah boundaries:** Existing logic handles searching for previous surah's last verse - preserve this.
